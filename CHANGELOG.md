## v1.0.0
### Added
- Operators can now turn record validation and the typed GraphQL validity filter on and off with `RECORD_VALIDATION_ENABLED` and `TYPED_GRAPHQL_VALID_ONLY`. Both default to `true`, so nothing changes until you set them. Turning validation off stores new records as `unvalidated` and skips the startup refresh, and the next startup after re-enabling reclassifies those records. Turning the filter off makes typed queries, subscriptions, and endorsement closure return records of every validation status, and typed record objects now expose `validationStatus` and `validationError` so clients can tell them apart. Disabling validation requires disabling the filter.
- Add opt-in record version history. Collections listed in RECORD_HISTORY_COLLECTIONS (exact NSIDs or prefix.* patterns, Tap mode) keep every observed version in a new record_version table (removed again when the record or its account is deleted), seeded on startup with a baseline row per existing record, and the new root recordHistory(uri, first, after) GraphQL query pages through them oldest first. History is off by default; migrations 015 and 016 add the table and its indexes.
- Add a valid-only partial index on records by collection and creation time (`idx_record_timeline_valid`), so collection-wide timeline reads that select only valid records, such as the GainForest feed service, no longer fetch and discard every invalid row. On PostgreSQL, a collection with many invalid records previously cost one random read per skipped row on a cold cache, enough to hit statement timeouts. Per-account reads (filtered by `did`) are not covered. PostgreSQL operators with large record tables should build the index out of band before deploying: run `CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_record_timeline_valid ON record (collection, record_created_at DESC, uri DESC) WHERE record_created_at IS NOT NULL AND validation_status = 'valid';`, wait for it to finish, and check that `SELECT indisvalid FROM pg_index WHERE indexrelid = to_regclass('idx_record_timeline_valid')` returns true. Deploying while that build is still running makes the migration time out after 5 seconds rather than block writes. If the build failed or was cancelled, the migration refuses to start: run `DROP INDEX CONCURRENTLY idx_record_timeline_valid;`, rebuild it, then restart. Without an out-of-band build, the migration builds the index itself and blocks writes to `record` while it does.
### Changed
- Add an Indigo-backed record validation gate that atomically stores raw records with validation metadata while typed GraphQL and typed subscriptions expose only valid data. Generic records, search, and raw subscriptions retain invalid and unknown-schema data for diagnostics; admin Lexicon changes are validated and staged for the next process snapshot, so operators must restart or redeploy to apply them and coordinate multi-replica rollouts so old and new snapshots do not serve concurrently. PostgreSQL operators with large record tables can pre-create the validation refresh paging index before rollout to avoid a write-blocking startup index build.
### Fixed
- Startup no longer fails when a saved Lexicon declares a boolean or integer `const`, such as `app.bsky.embed.record`. Previously these documents could not be parsed and stopped the server while it built the startup Lexicon set.
- Bundle the published `org.hypercerts.workscope.cel` Lexicon and its strong-reference dependency in backend container images. Deployments whose saved claim activity schema references this helper can now build a complete startup schema instead of failing during startup reference validation.
- Fix `endorsementClosure` so only validated badge awards, badge definitions, and badge responses affect the computed trust graph. Invalid or unclassified raw records remain available through generic queries but can no longer create or suppress endorsement edges.
- Startup no longer fails when the saved Lexicon set contains query, procedure, subscription, or permission-set Lexicons. These non-record documents are skipped with a warning because they are never used for indexing or record validation; malformed documents and unknown main definition types still fail startup.
- Speed up `sortBy: createdAt` on typed collection queries, including deep pages. For every collection whose Lexicon declares top-level `createdAt` as a datetime, required or optional, valid-only or unvalidated, the sort now uses an indexed column instead of sorting every row by `json->>'createdAt'`, which took seconds on large collections such as `app.gainforest.ac.audio`.

  What changes for API consumers:
  - `after` and `before` cursors are index bounds, so a page deep into a collection costs about what a first page does instead of rescanning everything before the cursor. `recordTimeline` pagination gets the same bound and now orders by the timestamp instead of its text form.
  - Ordering follows the actual timestamp (normalized to UTC, millisecond precision) rather than the raw string, so mixed offsets and precisions sort correctly.
  - Records whose `createdAt` is missing or not a valid datetime stay in the results and sort as the oldest: last with `sortDirection: DESC`, first with `ASC`, ordered by `uri` among themselves. Previously they came first on PostgreSQL for unvalidated `DESC` reads, and valid-only reads of a required datetime left them out.
  - Paging works across that boundary, existing cursors keep working, and a cursor whose value is not a valid datetime returns an error asking the client to restart pagination.
  - A record whose `createdAt` is later edited keeps its first-seen position, matching `recordTimeline`.
  - When `createdAt` is a required datetime and typed reads are valid-only (the default), full-datetime `where: { createdAt: ... }` filters use the same column at millisecond precision. Date-only values such as `"2026-01-01"` and `contains`/`startsWith` keep the previous string comparison.
  - A selective `where` filter on another field, such as a JSON field few records have, can still make the database walk much of the collection to find enough matches.

  What operators need to know:
  - Migration 018 adds `idx_record_collection_created_at` and `idx_record_collection_created_at_valid`, which also cover records without a `createdAt`, plus `idx_record_author_collection_created_at` for `where: { did: ... }` reads. Migration 019 drops the hand-made `idx_record_collection_json_created` if a deployment created it.
  - On PostgreSQL both run outside a transaction with `CREATE/DROP INDEX CONCURRENTLY`, so writes to `record` continue during the builds, and a restart finishes an interrupted migration.
  - Migrations run before the server starts listening. On a very large `record` table the three builds can outlast a deploy health check (240 seconds in `railway.toml`). A build killed that way leaves an INVALID index, and startup then stops until you run `DROP INDEX CONCURRENTLY <name>;` (the error names the index) and restart.
  - For large tables, pre-build the indexes out of band before deploying. Use exactly these definitions, because `IF NOT EXISTS` keeps any existing index with the same name and a different definition would be kept silently, leaving queries to sort:
    - `CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_record_collection_created_at ON record (collection, record_created_at DESC NULLS LAST, uri DESC);`
    - `CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_record_collection_created_at_valid ON record (collection, record_created_at DESC NULLS LAST, uri DESC) WHERE validation_status = 'valid';`
    - `CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_record_author_collection_created_at ON record (did, collection, record_created_at DESC NULLS LAST, uri DESC);`
  - Check `SELECT indisvalid FROM pg_index WHERE indexrelid = to_regclass('<name>')` returns true for each before deploying.
  - Rolling back the application does not run down migrations, and the 019 down migration cannot restore the dropped stopgap index because its definition is unknown. The new indexes are harmless to the previous version. If you roll back and relied on the stopgap for the old JSON `createdAt` sort, recreate it yourself.
  - The older partial indexes `idx_record_timeline_collection_created` and `idx_record_timeline_valid` are retained because PostgreSQL readers outside Hyperindex, such as the GainForest feed service, order `NULLS FIRST` and depend on them. Once those readers use `ORDER BY record_created_at DESC NULLS LAST, uri DESC`, which the new indexes serve and plain `DESC` does not, the old indexes can be dropped in a follow-up.

## v0.10.0

v0.10.0 adds structured author identity to GraphQL record queries and subscriptions. Consumers can now select both an author's DID and current handle without resolving handles separately.

### Structured record authors

Record results and subscription events now expose non-null `author { did handle }` metadata. `author.did` contains the record author's DID, while `author.handle` is null when Hyperindex does not have a current valid handle. Tap ingestion preserves handles already stored for actors and reconciles handles that earlier ingestion left empty or set to DID placeholders.

### Upgrade notes

- GraphQL consumers should migrate direct `did` selections to `author.did` and can use `author.handle` when they need the current handle. The direct `did` output remains available for compatibility but is deprecated; existing `where.did` filters are unchanged.
- Lexicon owners must rename any top-level record property named `author`. Hyperindex now reserves that name for structured identity metadata and does not expose a colliding Lexicon property or its generated filter.

## v0.9.2

v0.9.2 focuses on safer, lower-overhead maintenance for Hyperindex operators.

### Fixed

- Activity retention cleanup now runs when the service starts and every hour afterward, so long-running deployments continue deleting activity log entries older than seven days.
- Tap identity purges now delete an actor and its records in one transaction. If actor deletion fails, the transaction rolls back so both remain instead of leaving the identity partially purged.
- PostgreSQL migrations now remove the unused whole-document GIN index on record JSON, reducing index storage and write maintenance while preserving current query behavior.

## v0.9.1

v0.9.1 tightens up the new `endorsementClosure` query from v0.9.0. The query now handles messy badge-award data more defensively and reports large endorsement graphs more accurately.

### Fixed

- Endorsement closure results now ignore malformed badge-award subject DIDs instead of treating them as graph edges. In practice, bad or non-account subjects no longer leak into the endorsement path for an account.
- Certified profile hydration stays batched on SQLite, avoiding the large per-DID lookup path that could make endorsement closure responses slower on bigger result sets.
- The `truncated` flag is now set from the actual closure traversal result. If the server cap cuts off the graph, clients can trust `truncated: true`; if invalid edges were skipped and the graph still fits, it stays `false`.

## v0.9.0

v0.9.0 adds a GraphQL query for exploring Certified endorsement networks from a single account. It answers questions like "who does this account endorse?" and "who is reachable through those endorsements?" without making clients download every badge award and rebuild the graph themselves.

### Added

- Added `endorsementClosure(where, first, after)`, a bounded, forward-paginated connection rooted at one DID. Pass `where: { did: { eq: "did:plc:..." } }` to return active account endorsements up to three hops away. Use `where.degree.eq` to limit results to direct endorsements (`1`) or indirect hops (`2` or `3`).
- Returned accounts include `did`, `degree`, optional `certifiedProfileData`, and `viaAccounts` so clients can show the path that led to an indirect account. Results are ordered by degree and DID, include `totalCount`, and set `truncated` when the server cap cuts off part of the graph.
- The resolver only treats active Certified endorsement badge awards for account DID subjects as endorsement edges. It ignores record strong-ref subjects and respects badge-definition `allowedIssuers`, so restricted badge definitions only count endorsements from allowed issuers.

### Notes

- The closure is computed at request time from indexed badge award, badge definition, and badge response records. No separate endorsement edge table or backfill is needed.
- `endorsementClosure` is intentionally rooted at one DID, so the root DID filter only supports `eq`.

## v0.7.0

v0.7.0 makes label filtering work at the author/account level, not just on individual records. Existing `externalLabels` filters still match labels attached to a record AT-URI. New `authorLabels` filters match labels attached to the record author's DID, which is the shape used for account-quality labels such as `standard`, `high-quality`, or `likely-test`.

### For users

- Typed record connection queries now accept `where.authorLabels` next to the existing `where.externalLabels`. Use `externalLabels` for labels on the record itself, and `authorLabels` for labels on the author DID.
- `authorLabels` supports the same `has` and `none` predicates as `externalLabels`, including `src`, `val`, and `activeOnly`. Clients can require authors with a trusted label or exclude authors with a known test/spam label without filtering pages on the client.
- Filtering runs before `edges`, cursors, `pageInfo`, and `totalCount` are calculated. The page and count you receive describe the filtered result set.

Example: exclude authors marked as likely test accounts by a specific labeler.

```graphql
where: {
  authorLabels: {
    none: {
      src: { eq: "did:plc:pswneepkd5lesumj7ejmkbal" }
      val: { eq: "likely-test" }
      activeOnly: true
    }
  }
}
```

### Notes

- `authorLabels` only matches DID-subject labels, for example `uri: "did:plc:..."` with no CID. It does not infer labels from profile records, organization records, or other records by the same author.
- Unlabeled authors pass `none` filters and do not pass `has` filters.
- There is no node-level `authorLabels` field. To display labels for known author DIDs, query `externalLabels(subjects: [...])`.

## v0.6.0

v0.6.0 makes badge-award filtering more direct and removes a GraphQL filter shape that looked valid but could not actually run.

### Added

- Badge award queries now support a `badgeType` filter. Clients can fetch `app.certified.badge.award` records by the type of the referenced badge definition without joining badge definitions on the client.

## v0.5.0

v0.5.0 makes typed GraphQL filters more useful when clients already know the records or references they want. You can now batch hydrate records by AT-URI and filter inside common nested lexicon shapes without falling back to broad JSON search.

### For users

- Typed public record queries now include a metadata `uri` filter. Use `where: { uri: { eq: ... } }` for one known AT-URI, or `where: { uri: { in: [...] } }` to fetch a batch. The filter reads the stored record URI, not a `uri` key inside the JSON payload, so it still works when a lexicon has its own field named `uri`.
- Generated nested `where` filters now cover arrays, refs, and unions up to three lexicon path segments deep. This makes common relationship queries possible in GraphQL, such as finding collections whose `items` array contains a strong ref with a matching `itemIdentifier.uri`.
- Array `any` filters keep multiple predicates scoped to the same array item. A query that asks for both `itemIdentifier.uri` and `itemIdentifier.cid` only matches when both values are present on one array element, not split across different elements.
- Hypercert activity queries now include `contributorDid` for contributor matching. It covers inline contributor DIDs, legacy bare DID array entries, and `org.hypercerts.claim.contributorInformation` strong refs by checking the referenced record's `identifier`.

### Notes

- Nested scalar filters are exact-match only: `eq`, `in`, and `isNull`. Substring and range operators such as `contains`, `startsWith`, `gt`, and `lt` are intentionally not exposed for nested fields.
- Nested filters stay within the current record except for the activity-specific `contributorDid` compatibility filter. Use `search` or client-side filtering for deeper traversals or arbitrary JSON matching.

### Affects

- user
## v0.4.0

v0.4.0 makes Certified profile context easier to fetch, adds a Railway-friendly way to scrape Tap metrics, and fixes data formatting problems in large GraphQL reads and legacy backfills.

### For users

- Public record GraphQL nodes now include `certifiedProfileData`. Clients can fetch the author's Certified profile record and the external labels attached to that profile record alongside any indexed record.
- Large GraphQL pages with external labels now work more reliably on SQLite. Requests for up to 1,000 labeled records no longer exceed SQLite query limits.
- Legacy Go backfills now preserve AT Protocol CBOR values correctly. CID links, byte arrays, and blob references are stored using their canonical JSON shapes.

### For operators

- Hyperindex now includes a small Prometheus Railway service for scraping Tap metrics. Use it when Tap ingestion metrics need to be collected alongside the rest of the Railway deployment.
- Delete activity events now write empty or JSON `null` payloads as `{}`. This avoids PostgreSQL JSONB insert failures for delete events.

### Breaking change and upgrade notes

- The activity log table has been renamed from `jetstream_activity` to `indexing_activity`. The app runs this migration at startup.
- Update any direct SQL queries, dashboards, alerts, backups, or monitoring that still refer to `jetstream_activity`.
- Existing GraphQL queries do not need to change. Clients can opt into `certifiedProfileData` when they need Certified profile context.

## v0.3.0

This release makes Hyperindex easier to operate with external labelers and nicer to use when exploring the GraphQL API.

The biggest change is first-class support for external ATProto labelers. Hyperindex can now subscribe to configured `com.atproto.label.subscribeLabels` streams, keep resumable cursors, store the raw label events, and expose active labels through GraphQL. Clients can also filter generated record queries by external labels before pagination, so paging through labeled records is predictable instead of awkward.

### For users

- GraphiQL now includes the official Explorer plugin. You can build public and admin queries from the sidebar by checking fields instead of typing every query by hand.
- Record queries can filter on the presence of complex top-level lexicon fields.
- Malformed typed union values now resolve to `null` instead of failing the whole GraphQL response.
- GraphQL connection queries can return up to 1000 records per request, up from 100.
- Record-level `externalLabels` now works for CID-scoped records on PostgreSQL.

### For operators

- Admin settings and GraphQL now support removing configured external labeler subscription URLs.
- Labeler ingestion has safer subscription URL validation, log redaction, database indexes, and documentation for running the pipeline with Tap.
- Readiness checks now fail when a configured labeler hits a non-retryable cursor error, with diagnostics that explain what is stuck. `/health` stays process-only, while `/ready` checks the database and configured labeler diagnostics.
- There is an opt-in API smoke write-through check for testing ATProto create, update, and delete ingestion for Certified profiles and Hypercert activity claims.
- Backend Railway builds should be lighter thanks to a smaller Docker build context, the matching Go builder image, and stripped release binary debug metadata.
- Backend status endpoints now report the released Hyperindex version when the binary is built through the Makefile or Docker.
